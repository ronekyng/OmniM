# AMIR 规范 (AI 中间表示层)

## 1. 目的

AMIR (**A**I **M**iddle **I**ntermediate **R**epresentation) 是 OmniM 的 AI 翻译层，负责把**自然语言**转换为**类型化的 Omcom 命令**（`OmniCommand`，见 proto/omcom.proto）。

AMIR 的作用是纯粹的翻译——它不执行建模操作，也不定义指令格式，而是作为 AI 大模型与 Omcom 命令体系之间的桥梁：

```
自然语言 ──→ AMIR ──→ Omcom 命令（类型化 OmniCommand） ─→ Validator ─→ Executor ─→ 模型
(Prompt)                                                                        ↑
              │                                              模型状态 ──────────┘
模型状态 ─────┘ (反向解读 → 自然语言)
```

> 说明：「AMIR 输出 Omcom 文本 DSL」这一最初的构想保留为未来设计方向 —— 见
> [RFC-0001](../RFC/RFC-0001-omcom-text-dsl.zh-CN.md)。今日 AMIR 输出类型化命令，
> 代码库中也不存在文本解析器。

### 1.1 AMIR 不是什么

| AMIR 是 | AMIR 不是 |
|---------|-----------|
| 自然语言 → Omcom 命令的翻译器（类型化 OmniCommand） | 建模指令格式本身（那是 proto/omcom.proto） |
| AI 意图识别与参数提取器 | 指令执行引擎（那是 Executor） |
| 模型状态的自然语言解释器 | 撤销/重做管理器 |
| 多智能体协同编排器 | 验证器（那是 Omcom 层的职责） |

Omcom 是一个独立的分层，参见 [OMCOM_SPEC.md](OMCOM_SPEC.md)。

## 2. 核心设计原则

- **透明化**：AMIR 输出的是标准类型化 Omcom 命令，不引入 AI 特有的扩展
- **可追溯**：每条生成的 Omcom 指令都携带来源上下文（Actor = AI_AGENT）
- **高容错**：AI 可能出错，AMIR 层应通过结构化约束降低出错概率
- **领域适配**：不同工程领域（建筑、土木、工厂、机械）有各自的 prompt 模板
- **可解释**：AI 生成指令的理由以自然语言呈现给用户

### 3.1 Prompt 解析器

**职责**：接收用户的自然语言输入，提取意图和参数。

- **意图分类**：识别用户要执行的操作类型（创建对象、修改属性、删除元素等）
- **实体提取**：从自然语言中提取工程对象、属性、数值、单位等
- **上下文感知**：结合当前视口选择、历史对话等上下文信息
- **模糊消歧**：当用户输入存在歧义时，引导用户澄清

**输入**：自然语言文本（如"在楼层1上创建一堵 5 米长、3 米高的墙"）

**输出**：结构化的意图描述（JSON：意图 + 参数键值对）

### 3.2 Omcom 生成器

**职责**：将解析后的意图转换为类型化 OmniCommand 信封（`crates/amir/src/generator.rs`）。

- **指令映射**：意图 → 对应的 Omcom 动作与操作消息
- **多步规划**：复杂操作拆分为一组 OmniCommand 信封
- **参数补全**：补充默认参数、计算隐含参数
- **引用解析**：将自然语言中的对象引用（"那堵墙"、"楼层1"）解析为对象 ID

**输入**：结构化的意图描述（JSON）

**输出**：序列化的 `OmniCommand` 信封（线上形式为 JSON），Actor = AI_AGENT

```
示例：

输入 (JSON 意图):
  {
    "intent": "create_object",
    "object_type": "wall",
    "name": "wall_1",
    ...
  }

输出 (OmniCommand):
  { "action": CREATE_OBJECT,
    "actor": { "id": "amir", "type": AI_AGENT },
    "operations": [ { "create_object": { ... } } ] }
```

### 3.3 逆向解析器

**职责**：将当前模型状态或对象选择转换为自然语言描述。

- **对象描述**：从对象类型、几何、属性生成自然语言描述
- **变更摘要**：对比模型基线，生成变更的自然语言摘要
- **模型解读**：将复杂的工程模型结构以自然语言解释给用户
- **Omcom → 自然语言**：将已有的 Omcom 命令序列翻译回自然语言，供用户理解和确认
  （这是原始愿景"模型 → 文本"方向；完整的 model→text 逆向解析器若获批，将由
  [RFC-0001](../RFC/RFC-0001-omcom-text-dsl.zh-CN.md) 补充）

**应用场景**：
- AI 回答"当前模型里有什么？"
- 导入模型后 AI 解读："这个 IFC 文件包含 3 层楼、20 堵墙、10 根柱子…"
- 操作预览："以下是对模型将要做的修改…"

### 3.4 多智能体编排器

**职责**：协调多个领域专用智能体，完成复杂的跨领域任务。

- **领域智能体**：
  - 建筑智能体（熟悉墙、梁、板、门、窗等建筑元素）
  - 土木智能体（熟悉道路、桥梁、隧道等土木元素）
  - 工厂智能体（熟悉储罐、管道、阀门等工厂元素）
  - 机械智能体（熟悉零件、装配、齿轮等机械元素）
- **编排逻辑**：根据用户输入的领域，路由到对应的智能体
- **结果合并**：跨领域操作的结果整合为统一的 Omcom 命令序列
- **冲突解决**：当不同智能体的输出存在冲突时，协调解决

### 3.5 验证反馈

**职责**：当 Omcom 验证失败时，将错误信息翻译回自然语言。

- **错误解释**：将验证器的结构化错误转换为用户易懂的自然语言
- **修正建议**：基于错误类型和上下文，给出修改建议
- **AI 重试**：在简单错误情况下，AMIR 可自动修正后重试
- **人在回路**：复杂或高风险操作，提请用户确认

## 4. AI 集成

### 4.1 LLM 集成方式

AMIR 支持多种 LLM 集成方式：

| 方式 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| Function Calling | OpenAI / Anthropic | 结构化输出，可靠性高 | 依赖云端 |
| 本地 LLM | Llama 3 / Qwen | 数据不出域，离线可用 | 能力相对较弱 |
| Prompt Template | 所有 LLM | 通用性强 | 输出不稳定，需二次校验 |

### 4.2 结构化输出

AMIR 内部使用 JSON 进行结构化意图表示，**最终输出是类型化的 Omcom 命令**（序列化
OmniCommand）。完整管线：

1. LLM 返回结构化 JSON（通过 Function Calling 或 JSON Mode）
2. AMIR 处理 JSON 意图
3. AMIR 生成类型化 OmniCommand 信封作为最终输出

```
LLM 输出 (JSON 结构化意图):
  {
    "intent": "create_wall",
    ...
  }

AMIR 输出 (OmniCommand 信封, JSON):
  { "action": CREATE_OBJECT, "actor": {"type": "AI_AGENT"}, ... }
```

### 4.3 RAG 增强

针对工程标准和规范查询，AMIR 支持检索增强生成：

- 嵌入工程规范、标准文档
- 当用户查询涉及规范时，检索相关条款作为 prompt 上下文
- 确保 AI 生成的建模指令符合工程规范

## 5. 反向解析 (模型 → 命令)

模型状态或对象选择可转换回自然语言描述（概念上也包含模型 → Omcom 命令日志），这使：
- AI 能够解读现有设计
- 对导入模型与生命周期数据做自然语言检索
- 变更检测和差异比较
- 指令级版本控制（完整的 model → OmniCommand 脚本逆向解析器属于原始愿景，见
  [RFC-0001](../RFC/RFC-0001-omcom-text-dsl.zh-CN.md)；其中描述了"模型 → 文本"的可渲染性）

### 反向解析策略
1. **几何简化**：尽可能将复杂几何转换为参数化表示
2. **对象分类**：识别并分类对象到适当的 ObjectType
3. **属性提取**：提取属性和属性集
4. **关系检测**：发现包含和连接关系
5. **指令排序**：按逻辑顺序排列操作（创建 → 修改 → 连接）

## 6. 版本与兼容性

AMIR 本身作为一个纯翻译层，其版本与 LLM 集成接口相关：
- **AMIR v1**：基于 Function Calling 的结构化输出，生成类型化 OmniCommand 命令
- 版本兼容性由对应的 Omcom schema（`omcom.proto`）保证
