# OmniM 前端完成定义（DoD）

> **文档定位。** 本文是流程层：定义功能、面板、文档与发布的"完成"含义。它把 [RELEASE_READINESS](../status/RELEASE_READINESS.zh-CN.md) 中的门禁转成工程师可执行的清单。
>
> **双轨维护义务**：`DEFINITION_OF_DONE.zh-CN.md` 是持续维护的译文。清单项与门禁定义必须一致。
>
> **规则。** "完成"是二值的。未勾选的 MUST 项意味着未完成，与演示效果无关。

## 1. 目的

当"完成"意味着"在我机器上跑通过一次"时，团队交付的是 demo。本文消除前端的这种模糊性。

## 2. 功能 DoD

功能在以下条件满足时算功能完成：

- [ ] 需求 ID 已登记，并链接到契约。
- [ ] 正常路径端到端可用，对接真实服务而非 mock。
- [ ] 校验以具体、本地化的消息拒绝非法输入。
- [ ] 取消操作不留下部分状态。
- [ ] 撤销能恢复先前状态，或界面声明该操作不可撤销。
- [ ] 空、加载、错误三态已实现。
- [ ] 权限/可用性规则在服务端强制，并在界面体现。
- [ ] 功能可键盘操作。

## 3. 界面 DoD

界面在以下条件满足时算界面完成：

- [ ] 只使用语义令牌；无硬编码颜色、间距、圆角或阴影。
- [ ] 在深色与浅色主题下可用，可访问性范围内还需高对比。
- [ ] 所有字符串来自 i18n 词典。
- [ ] 每个交互元素具备默认/悬停/按下/选中/禁用/聚焦态。
- [ ] 焦点顺序合理且可见；弹窗限制并归还焦点。
- [ ] 纯图标控件有可访问名称。
- [ ] 1280×720 与 1920×1080、100% 与 150% DPI 下布局成立。
- [ ] 不使用原生浏览器弹窗。
- [ ] 双主题截图已存在。

## 4. 文档 DoD

文档在以下条件满足时算完成：

- [ ] front matter 含 `title`、`status`、`last_updated`、`applies_to`、`evidence`。
- [ ] 中英文件的标题数量与编号完全一致。
- [ ] 所有相对链接可解析（`scripts/check_docs.py`）。
- [ ] 需求 ID 与 [REQUIREMENTS_REGISTER](../product/REQUIREMENTS_REGISTER.zh-CN.md) 一致。
- [ ] 关于现状的论断引用文件或实测计数。
- [ ] 含非目标与待定问题。
- [ ] `check_docs.py` 通过。

## 5. 测试 DoD

变更在以下条件满足时算测试完成：

- [ ] 单元测试覆盖纯逻辑（状态机、命名、单位、格式化）。
- [ ] e2e 测试覆盖用户可见路径。
- [ ] 影响布局的变更进入视觉回归。
- [ ] 变更面通过可访问性检查。
- [ ] 性能未超过 [PERFORMANCE](../specification/ui/PERFORMANCE.zh-CN.md) §8 的容差。
- [ ] 新代码路径出现在需求登记册的验证列。

## 6. 发布 DoD

候选版本在以下条件满足时算完成：

- [ ] 目标门禁分配的全部 **MUST** 需求为 `✅`；SHOULD 延期按 §8 处理。
- [ ] [RELEASE_READINESS](../status/RELEASE_READINESS.zh-CN.md) 中该门禁无阻塞问题。
- [ ] `check_docs.py`、`check_ui_contracts.py`、类型检查、单元、e2e、视觉、可访问性、性能任务全部通过。
- [ ] 成熟度分数达到门禁目标。
- [ ] CHANGELOG 有面向用户的条目。
- [ ] 已知问题有记录与临时方案。
- [ ] 诊断导出可用且不含模型数据。
- [ ] 回滚或恢复流程有文档。

## 7. 门禁定义

### 7.1 G0 — 契约就绪

需求、契约与非目标完成评审并签字。不需要生产代码，但在本门禁之前不得开始编码，除非是明确标注为一次性的技术验证。

### 7.2 G1 — Alpha

主旅程（打开/创建 → 建模 → 保存 → 重开）可用。没有白屏、没有原生弹窗、没有静默数据丢失、没有时间戳命名。内部用户能完成真实任务。

### 7.3 G2 — Beta

产品在外观与行为上像商用软件：有主题、已本地化、关键路径可访问、性能在预算内、每个失败都有说明。外部试点用户无需手把手即可工作。

### 7.4 G3 — GA

产品可支持：兼容性已声明、安全已披露、遥测已同意、诊断可导出、帮助可用、合规产物已写。

## 8. 例外流程

| 情况 | 流程 |
|---|---|
| MUST 需求无法满足 | 书面决策，写明范围、责任人、到期日与用户影响；需求仍为 `MUST`，门禁顺延 |
| SHOULD 需求延期 | 在发布说明中记录；最多延后一个次要版本 |
| 契约变更 | 在一个 PR 中同时更新契约、登记册与变更日志 |
| 紧急修复绕过清单项 | 合并后建 issue，写明日期，由门禁责任人批准 |

例外绝不静默改变需求优先级。

## 9. 非目标

1. 覆盖后端与前端的单一通用清单。
2. 强制结对编程或评审次数。
3. 为指标而指标。
