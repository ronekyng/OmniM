## Concurrency, Authentication, and Real-Time

- **No authentication.** The server is designed for local / single-user use. There are no API keys, sessions, or tokens.
- **No WebSocket / real-time collaboration.** OmniM exposes **REST only**. There is no live-sync, no event streaming, no presence. Poll `GET /api/tree` or `GET /api/objects` when you need fresher state; the web UI simply refetches after each mutation.
- **Single project in memory.** All routes operate on one shared `Project` held behind an `Arc<RwLock<Project>>` (`SharedProject`). Reads share the read lock; writes take the write lock, so mutations are serialized.
- **Undo/Redo backend (✅ complete).** Every mutating endpoint goes through the Omcom executor and pushes undo/redo history, surfaced by `GET /api/undo-status`. IFC import is one whole-project transaction (`Command::ReplaceProject`); `.omnimlib` import into the global library and the `section_handler` cache lock are the only documented exceptions (see [WRITE_PATHS](../architecture/WRITE_PATHS.md)). Mutations persist by default; `POST /api/project/save` flushes explicitly and `OMNIM_EPHEMERAL=1` disables writes.

## Base URL Conventions

- **Default base URL**: `http://0.0.0.0:3000` — the server binds `0.0.0.0` (all interfaces) on port `3000`. Use `http://localhost:3000` from the same machine.
- **Environment variables** (read in `crates/server/src/main.rs`):

  | Variable | Default | Purpose |
  |---|---|---|
  | `OMNIM_HOST` | `0.0.0.0` | Bind address |
  | `OMNIM_PORT` | `3000` | HTTP port |
  | `OMNIM_PROJECT` | `project.omnim` | Project file loaded at startup; also used as the auto-save path (auto-save is skipped for the default file). |
  | `AMIR_PROVIDER` / `AMIR_API_KEY` / `AMIR_MODEL` | — | Configure the AMIR AI engine (`/api/amir/*`); without them the AMIR endpoints return `501`. |

- **Request bodies** are `application/json` (UTF-8) except `POST /api/import/ifc`, which takes raw IFC text.
- **Responses** are `application/json` except `GET /api/export/ifc` (`application/ifc`) and `GET /api/health` (plain text).
- Many request/response types (`OmniObject`, `OmniCommand`, `Point3D`, `Material`, `Project`, `ExecutionResult`, …) are **protobuf-derived Rust types** (prost) serialized with `serde`: snake_case JSON keys, repeated fields as JSON arrays, enums as integers (`"object_type": 1`). Tag values live in the generated bindings in `omnim_core`.
- Request body limit: **100 MB** (`DefaultBodyLimit::max(100 * 1024 * 1024)`), sized for large IFC imports.
- A curated TypeScript client mirroring this API lives in `web/src/shared/api.ts`.

```bash
BASE=http://localhost:3000
```


## Model Objects and Properties

| Method & Path | Purpose |
|---|---|
| `GET /api/objects` | List all objects. |
| `POST /api/objects` | Create an object. |
| `GET /api/objects/{id}` | Fetch one object. |
| `PUT /api/objects/{id}` | Update name/description/IFC class/tags. |
| `DELETE /api/objects/{id}` | Delete an object (undoable). |
| `PUT /api/objects/{id}/prop` | Set a single string property. |
| `PUT /api/objects/{id}/properties` | Bulk update fields + properties. |
| `GET /api/object-types/{type}/properties` | Property definitions for a type. |

- `POST /api/objects` body (`CreateObjectRequest`):

  ```json
  {
    "object_type": "wall",
    "name": "North wall",
    "description": "optional",
    "ifc_class": "IfcWall",
    "tags": ["facade"],
    "geometry": { "operations": [ /* ParametricGeometry, optional */ ] },
    "parent_id": "optional-parent-id",
    "elevation": 3.9,
    "level_id": "optional-storey-object-id"
  }
  ```

  `object_type` accepts (case-insensitive): `wall`, `slab`, `roof`, `floor`, `beam`, `column`, `door`, `window`, `road`, `pipe`, `duct`, `cabletray`, `tank`, `pump`, `valve`, `gear`, `part`, `assembly`, `component`. Unknown names cause the Omcom creation op to record an unspecified type — prefer a listed value. The request is routed through an internal Omcom `CreateObject` command (recorded for undo), then `ifc_class`, `tags`, and `parent_id` are applied afterwards. `elevation` is the datum height in metres (meaningful on `storey`, IfcBuildingStorey.Elevation); `level_id` attaches the object to an existing `BuildingStorey` and is validated (unknown id or non-storey target → `400` with the reason). Response: the created `OmniObject`; `400` with the validator's reason on validation failure, `500` only for internal errors.

- `OmniObject` JSON shape (protobuf-derived): `{ id, name, description, object_type (int enum), status (int), properties[], property_sets[], geometry (Geometry or null), material_id, parent_id, tags[], ifc_class, features[], sketch_ids[], dirty, catalog_ref, elevation (number or null, P8-S1), level_id (string or null, P8-S1) }`.
- `PUT /api/objects/{id}` body: `{ name?, description?, ifc_class?, tags?, elevation?, level_id?, bottom_level_id?, top_level_id? }` (`""` clears an attachment; extent refs are both-or-neither) → empty success, `404` if not found. All fields are undo/redo covered (P8-S1 extended the `ModifyObject` snapshot to every modifiable field).
- `PUT /api/objects/{id}/prop` body: `{ "name": "FireRating", "value": "2h" }` — values are stored as string `PropertyValue`s. → empty success, `404`.
- `PUT /api/objects/{id}/properties` body: the `PUT /api/objects/{id}` shape plus `"properties": { "k": "v", ... }` (string→string map). Useful for one-shot sync from editors. → empty success.
- `GET /api/object-types/{type}/properties` → `Vec<ObjectPropertyDef>`; unknown type → empty list.

```bash
# Create a wall
curl -sS -X POST "$BASE/api/objects" -H 'Content-Type: application/json' \
  -d '{"object_type":"wall","name":"North wall","ifc_class":"IfcWall","tags":["facade"]}'

# Set one property
curl -sS -X PUT "$BASE/api/objects/obj-1/prop" -H 'Content-Type: application/json' \
  -d '{"name":"FireRating","value":"2h"}'
```

## Geometry and Transform

| Method & Path | Purpose |
|---|---|
| `PUT /api/objects/{id}/transform` | Translate / rotate / scale the object's mesh geometry. |

- Body (`TransformObjectRequest`), all fields optional:

  ```json
  {
    "origin": { "x": 0, "y": 0, "z": 0 },            // pivot; defaults to mesh bbox center
    "translation": { "x": 1, "y": 0, "z": 0 },
    "rotation": { "x": 0, "y": 0, "z": 0, "w": 1 },  // quaternion
    "scale": { "x": 2, "y": 1, "z": 1 }
  }
  ```

  Composite transform: shift by `−origin`, apply translation/rotation/scale, shift back by `+origin`. Any geometry representation is converted to a mesh, transformed, bbox recomputed, and the object geometry rewritten as a `Mesh`. → empty success; `404` unknown object, `400` no geometry.

|---|---|
| `GET /api/materials` | List materials. |
| `POST /api/materials` | Create a material. |
| `PUT /api/objects/{id}/material` | Assign a material to an object. |

## Measurements

| Method & Path | Purpose |
|---|---|
| `GET /api/measurements` | List saved measurements. |
| `POST /api/measurements` | Create a measurement. |
| `DELETE /api/measurements/{id}` | Delete a measurement. |

- `POST /api/measurements` body (`CreateMeasurementRequest`):

  ```json
  { "type": "distance", "points": [{ "x":0,"y":0,"z":0 }, { "x":3,"y":0,"z":0 }],
    "value": 3.0, "label": "Room width", "color": "#44ff88" }
  ```

  `type` is a free string (commonly `distance`, `area`, `angle`, `volume`); `color` defaults to `#44ff88`. Response: the created `Measurement` (`{ id, type, points, value, color, label }`). `DELETE` → empty success, `404` unknown id.

- **Level-driven vertical extent (P8-S2).** Objects can carry `bottom_level_id` + `top_level_id` (`POST`/`PUT /api/objects`, and the `layered` genrule variant). Both-or-neither; each must reference a `BuildingStorey`; top’s elevation must be above bottom’s (a storey without elevation counts as 0 m). Resolution sets `elevation` to the bottom level and — for path-driven (`PathSweep`) geometry, the Wave-3 building family — shifts the path base and sets the sweep height to `top − bottom`. Plain box geometry receives the `elevation` datum only. Changing a storey’s `elevation` re-resolves every constrained object as **one undo step**. Deleting a storey still referenced by objects is rejected with `400` (detach first).

## Grid Datum

Grid lines (轴网) are **datum annotations, not objects** — they carry no mesh, live outside the object tree, and are stored in `Project.grids` (P8-S1). Like measurements they are undoable and persist with the project.

| Method & Path | Purpose |
|---|---|
| `GET /api/grids` | List grid lines, sorted AlongX (numbered) then AlongY (lettered) by coordinate. |
| `POST /api/grids` | Create a grid line. → `201` with the created line. |
| `PUT /api/grids/{id}` | Full-replacement update. → `404` unknown id. |
| `DELETE /api/grids/{id}` | Delete (undoable). → `404` unknown id. |

- `POST`/`PUT` body (`GridLineRequest`):

  ```json
  { "label": "A", "axis": "along_y", "coordinate": -3.0,
    "extent_min": 0.0, "extent_max": 24.0 }
  ```

  `axis` is `along_x` (line parallel to X at `y = coordinate`, the numbered family) or `along_y` (line parallel to Y at `x = coordinate`, the lettered family); `extent_min/max` default to `0` (unbounded in the UI). Labels are unique **per axis family** (duplicate → `400`); an empty label or unknown axis → `400`. Response shape: `{ id, label, axis: "AlongX" | "AlongY", coordinate, extent_min, extent_max }`.

## IFC Import and Export

| Method & Path | Purpose |
|---|---|
| `GET /api/export/ifc` | Export the whole project as IFC text. |
| `POST /api/import/ifc` | Import IFC text into the project. |

- `GET /api/export/ifc` → `200` with `Content-Type: application/ifc` and `Content-Disposition: attachment; filename="project.ifc"` (raw IFC STEP text).
- `POST /api/import/ifc` — body is **raw IFC text**, not JSON. The 100 MB body limit exists mainly for this route.
  - Supported input is an **IFC 2x3 / IFC 4 subset** only (see [FORMAT_COMPAT](../status/FORMAT_COMPAT.md)); there is no IFC 4x3-specific entity support, material/quantity/classification mapping, or lossless round-trip guarantee.
  - Query params: `normalize` (default `true` — recenter imported geometry at the origin) and `mode` (`merge` default | `replace` — swap the entire project).
  - Response `ImportIfcResponse`: `{ success, imported, objects, message }`. Parse failures come back as HTTP `200` with `success: false` in the body.

```bash
# Export
curl -sS "$BASE/api/export/ifc" -o project.ifc

# Import (raw text body)
curl -sS -X POST "$BASE/api/import/ifc?normalize=true&mode=merge" \
  --data-binary '@model.ifc' -H 'Content-Type: text/plain'
```

## Sketch System

Sketches are 2D profiles attached to the project (optionally to a Component) and can be extruded/revolved into 3D parts.

| Method & Path | Purpose |
|---|---|
| `GET /api/sketches` | List sketches (optionally `?component_id=`). |
| `POST /api/sketches` | Create a sketch. |
| `GET /api/sketches/{id}` | Get full sketch (entities + constraints). |
| `PUT /api/sketches/{id}` | Rename / move origin. |
| `DELETE /api/sketches/{id}` | Delete a sketch (undoable). |
| `POST /api/sketches/{id}/entities` | Add an entity (point/line/circle/...). |
| `POST /api/sketches/{id}/constraints` | Add a constraint. |
| `POST /api/sketches/{id}/solve` | Run the constraint solver. |
| `PUT /api/sketches/{id}/entities/{idx}` | Update an entity. |
| `DELETE /api/sketches/{id}/entities/{idx}` | Remove an entity. |
| `DELETE /api/sketches/{id}/constraints/{idx}` | Remove a constraint. |
| `POST /api/sketches/{id}/extrude` | Extrude the profile into a 3D Part. |
| `POST /api/sketches/{id}/revolve` | Revolve the profile around an axis. |

- `POST /api/sketches` body: `{ "name": "Facade profile", "origin": { "x":0,"y":0,"z":0 }, "normal": { "x":0,"y":0,"z":1 }, "component_id": null }` — `component_id` must reference an existing Component (else `400`). Response `SketchResponse`: `{ id, name, origin, normal, entity_count, constraint_count, solved, component_id }`.
- `GET /api/sketches/{id}` → the full `omnim_sketch::Sketch` (`{ id, name, origin, normal, entities[], constraints[], solved, component_id }`).
- `POST .../entities` body (`AddEntityRequest`): `{ "entity_type": "circle", "points": [{ "x":1,"y":0,"z":0 }], "radius": 0.5, "sides": 0, "construction": false }`. `entity_type` ∈ `point | line | circle | arc | rectangle | polygon | ellipse | spline | polyline`; `radius`/`sides` apply to circle/polygon-ish types; `construction` marks construction geometry. Response: `{ "index": 0 }` (entity index within the sketch).
- `POST .../constraints` body (`AddConstraintRequest`): `{ "constraint_type": "length", "entity_refs": [[0,0],[0,1]], "value": 3.5 }`. `entity_refs` are `[entity_index, point_index]` pairs. `constraint_type` ∈ `horizontal, vertical, coincident, parallel, perpendicular, length, distance, angle, radius, diameter, tangent, symmetric, fixed, at_midpoint, equal_length, equal_radius, pt_on_line, pt_on_circle, same_orientation`. Response `{ "index": 0 }`.
- `POST .../solve` → `SolveResponse`: `{ "success": true, "dof": 0, "message": "..." }`.
- `PUT .../entities/{idx}` body (`UpdateEntityRequest`): `{ points?, radius?, sides?, construction? }` → `204`/empty; `404` bad index.
- `POST .../extrude` body: `{ "depth": 2.5, "direction_x": 0, "direction_y": 0, "direction_z": 1 }` (direction defaults to sketch normal +Z). Auto-solves first. Response `FeatureResponse`: `{ success, message, vertices, faces, object_id }` — a new `Part` object named `extrude-<sketch>` is created. `400` if sketch unsolvable or profile invalid.
- `POST .../revolve` body: `{ "angle": 360, "axis_origin_x": 0, "axis_origin_y": 0, "axis_origin_z": 0, "axis_direction_x": 0, "axis_direction_y": 1, "axis_direction_z": 0 }` (axis defaults to origin / (0,0,1)). Same `FeatureResponse` shape; creates a `Part` named `revolve-<sketch>`.

```bash
# Create sketch, draw a rectangle, solve, extrude
SID=$(curl -sS -X POST "$BASE/api/sketches" -H 'Content-Type: application/json' \
  -d '{"name":"Pad"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

curl -sS -X POST "$BASE/api/sketches/$SID/entities" -H 'Content-Type: application/json' \
  -d '{"entity_type":"rectangle","points":[{"x":0,"y":0,"z":0},{"x":2,"y":1,"z":0}]}'

curl -sS -X POST "$BASE/api/sketches/$SID/solve"
curl -sS -X POST "$BASE/api/sketches/$SID/extrude" -H 'Content-Type: application/json' \
  -d '{"depth":1.5}'
```

## Components and Features

Components are parametric feature-tree parts; features replay sketches (extrude/revolve/sweep/loft/boolean/…).

| Method & Path | Purpose |
|---|---|
| `GET /api/components` | List components. |
| `POST /api/components` | Create a component. |
| `GET /api/components/{id}` | Get one. |
| `DELETE /api/components/{id}` | Delete one. |
| `GET /api/components/{id}/features` | List features. |
| `POST /api/components/{id}/features` | Add a feature. |
| `PUT /api/components/{id}/features/{fid}` | Update a feature. |
| `DELETE /api/components/{id}/features/{fid}` | Remove a feature. |
| `POST /api/components/{id}/rebuild` | Rebuild the feature tree. |
| `GET /api/components/{id}/section` | Compute horizontal section lines (`?plane_z=`). |

- Items are `ComponentResponse`: `{ id, name, feature_count, sketch_ids, parent_id }`.
- `POST /api/components` body: `{ "name": "Bolt", "parent_id": null }`.
- Items of the features list are `FeatureResponseItem`: `{ id, name, feature_type, sketch_id, input_sketch_ids, axis_sketch_id, depth, angle, is_cut, order, suppressed, dirty }`.
- `POST .../features` body (`AddFeatureRequest`):

  ```json
  { "feature_type": "extrude", "sketch_id": "sk-1", "input_sketch_ids": [],
    "axis_sketch_id": null, "depth": 2.0,
    "direction_x": 0, "direction_y": 0, "direction_z": 1,
    "angle": 0, "is_cut": false, "lod": 1e-6 }
  ```

  `feature_type` ∈ `extrude | revolve | sweep | loft | fusion | lofted_fusion | boolean | chamfer | fillet | pattern | shell` (unknown → `extrude`). The referenced sketch must exist (`404` otherwise); the component rebuilds automatically after add/update/remove. Response: the created `FeatureResponseItem`.
- `PUT .../features/{fid}` body (`UpdateFeatureRequest`): any of `sketch_id, axis_sketch_id, depth, angle, is_cut, suppressed, input_sketch_ids, dependency_ids, direction, axis_origin, axis_direction, lod, boolean_op` (int: `0=union`, `2=intersect`, else `subtract`), `pattern_count_x/y/z` → `{ "success": true }`.
- `GET .../section?plane_z=0.0` → `Vec<SectionLine>` (2D polylines of the horizontal cut at world Z = `plane_z`), computed from all feature geometries merged.

- `POST /api/catalog` body: `{ "name": "PB Pipe", "category": "pipe", "description": "...", "ifc_class": "IfcPipeSegment", "standard_reference": "", "tags": [], "domain": "" }` → created `ComponentDef`.

- `POST .../connectors` body (`AddConnectorRequest`): `{ "connector_id": "c1", "connector_name": "inlet", "position_x_expr": "0", "position_y_expr": "0", "position_z_expr": "L/2", "direction_x_expr": "0", "direction_y_expr": "0", "direction_z_expr": "1", "bore_expr": "bore", "connection_type_code": "", "role": 0 }` — position/direction/bore are expressions evaluated at instantiation time → `201`.
- `PUT .../feature-tree` body: `{ "feature_tree_id": "..." }`; `POST .../publish` has no body (sets `published = true`) → `200`.
- `POST /api/catalog/export` (no body) → `{ "path": "/tmp/omnimlib-<ts>.omnimlib", "component_count": 3 }`.
- `POST /api/catalog/import` body: `{ "path": "/tmp/omnimlib-....omnimlib" }` → `{ "component_count": 3, "names": ["..."] }`; `400` if the file can't be loaded.
- `POST /api/catalog/instantiate` body (`InstantiateRequest`):

  ```json
  { "component_def_id": "def-1", "instance_name": "Pipe A",
    "params": { "length": 2000, "bore": 100 },
  ```

- `POST /api/catalog/preview` body: `{ "component_def_id": "def-1", "params": {...} }` → `c::MeshGeometry` (vertices/normals/uvs/faces), scaled from millimetres to metres; the temporary instance is removed before the response. ## Series

Series model code-driven selection logic for standard components: a decision tree of selectors/answers whose leaves are `SpecComponent`s (catalog definitions + parameter constraints).

| Method & Path | Purpose |
|---|---|
| `GET /api/series` | List series. |
| `POST /api/series` | Create a series. |
| `POST /api/series/save` | Save all series to a timestamped `.omnimseries` file. |
| `POST /api/series/load` | Load series from an external file. |
| `GET /api/series/{id}` | Get one. |
| `PUT /api/series/{id}` | Update one. |
| `DELETE /api/series/{id}` | Delete one. |
| `POST /api/series/{id}/selectors` | Add the root selector (first call only). |
| `POST /api/series/{id}/answers` | Add an answer to a selector. |
| `POST /api/series/{id}/spec` | Bind an answer to a catalog component. |
| `POST /api/series/{id}/constraints` | Add a parameter constraint. |
| `PUT /api/series/{id}/constraints/{idx}` | Update a parameter constraint. |
| `DELETE /api/series/{id}/constraints/{idx}` | Remove a parameter constraint. |
| `POST /api/series/{id}/select` | Run the selection engine. |

- Items are `omnim_model::series_store::Series`: `{ id, name, description, domain, standard_reference, applicable_phases, metadata, root_selector, ... }`.
- `POST /api/series` body: `{ "name": "Pipe series", "description": "", "domain": "", "standard_reference": "" }` → created `Series`.
- `POST /api/series/save` (no body) → `{ "path": "/tmp/omnimseries-<ts>.omnimseries", "saved_count": 2 }`.
- `POST /api/series/load` body: `{ "path": "/path/to/file.omnimseries", "source": "standalone" }` → `{ "loaded_count": 2, "series_names": ["Pipe series"] }`; series are tracked in `external_series_refs`.
- `POST .../selectors` body: `{ "selector_id": "s-material", "question": "Which material?" }` — only the first call per series sets `root_selector`; later calls are accepted but inert → `201`.
- `POST .../answers` body (`AddAnswerRequest`): `{ "selector_id": "s-material", "answer_id": "steel", "answer_value": "steel", "is_numeric_range": false, "range_min": 0, "range_max": 0 }` — linked selectors are followed: the answer's outcome initially points to no component; use `/spec` or a subsequent `/answers` on the newer selector to bind it. → `201` if the selector is found (search walks the tree); `404` otherwise.
- `POST .../spec` body: `{ "selector_id": "s-material", "answer_id": "steel", "component_def_id": "def-1", "material": "steel-s235", "connection_type_code": "" }` → `201` if found; `404` otherwise.
- `POST .../constraints` body (`AddParamConstraintRequest`): `{ "component_def_id": "def-1", "param_name": "length", "default_value": 1000, "min_value": 100, "max_value": 5000, "step": 10, "fixed_value": "" }` → `201` (constraint appended to the matching `SpecComponent`); `404` otherwise.
- `PUT|DELETE .../constraints/{idx}`: same framing; body carries `component_def_id` to locate the spec component, and `idx` addresses the index within its `param_constraints` array.
- `POST .../select` body: `{ "answers": ["steel", "dn50"] }` (answer ids/values walked against the decision tree) → `SelectResponse`: `{ "component_def_id", "selector_path", "spec_component" }`; `400` when the tree doesn't fit the given answers.

```bash
# Run a series selection
curl -sS -X POST "$BASE/api/series/ser-1/select" -H 'Content-Type: application/json' \
  -d '{"answers":["steel","dn50"]}'
```

## GenRule

`POST /api/genrule` — declarative one-shot object generation via GenRule engines (LayerExtrusion, LinearComponent, Primitive/Assembly, BooleanSubtract).

| Method & Path | Purpose |
|---|---|
| `POST /api/genrule` | Generate an object from a declarative rule. |

- Body is a **tagged enum** (`GenRuleRequest`): the JSON `type` field is one of `wall | slab | road | pipe | door | window | assembly | layered | line` and the remaining fields depend on that variant:

  | type | Key fields |
  |---|---|
  | `wall` | `name`, `length`, `height`, `core_thickness`, `finish_thickness`, `start_x/y/z`, `end_x/y/z`, `parent_id?`, `series_id?` |
  | `slab` | `name`, `length`, `width`, `structural_thickness`, `finish_thickness`, `parent_id?`, `series_id?` |
  | `road` | `name`, `length`, `width`, `thickness`, `parent_id?`, `series_id?`; optional `alignment` (picked polyline as `Path(open)`, `[x,y,z]` in metres, default empty). With ≥ 2 points the road is generated per segment along the polyline (each segment `build_road`-meshed, rotated by its segment angle and translated to the segment start, using the same `width`/`thickness`); with < 2 points the single straight road of `length` is generated. The polyline may arrive as contract `path { points, closed: false }` or legacy `alignment[]` — see the path contract below. |
  | `pipe` | `name`, `length`, `radius`, `parent_id?`, `series_id?` — legacy straight pipe; add `path` (`{ points, closed:false }`, ≥ 2 points) for **pipe routing** (P8): a circular section is swept along the polyline with mitered joints, stored as a `PipePlant` object with `route_points`/`pipe_radius` properties. `radius ≤ 0` → `400`. |
  | `door` / `window` | `name`, `wall_id`, `opening_width`, `opening_height`, `position_x`, `position_z`, `parent_id?` (parented to the wall; boolean-subtracted opening from the wall bbox) |
  | `opening` | `name`, `wall_id` (host **must** be a `Wall`), `opening_width`, `opening_height`, `position_x`, `position_z`, `parent_id?` — creates an `ObjectType::Opening` void volume (IfcOpeningElement) parented to the wall; the host mesh is not re-cut |
  | `assembly` | `name`, `components[]` of `{ name, shape: box\|cylinder\|sphere\|cone, p1, p2, p3, tx, ty, tz }`, `parent_id?` |
  | `layered` | `name`, `mode` (`wall\|slab\|roof\|floor`), `length`, `width`, `height`, `layers[]` of `{ name, thickness, material_id, function }`, `path` / `boundary` (see the path contract below), `start_*`/`end_*`, `parent_id?`, `series_id?`, `bottom_level_id?`/`top_level_id?` (P8-S2 vertical extent — validated **before** creation, so an invalid pair cannot leave an orphan object; `series_id` is metadata only on this family) |
  | `line` | `name`, `path` / `alignment` (see the path contract below, ≥ 2 points), `diameter`, `parent_id?` — generates a thin guide tube (`FeatureLine`) |

  **Path contract (2026-10-28, DATA_MODEL §1).** Path-shaped inputs accept the
  contract form `{ "points": [[x,y,z],…], "closed": bool }` **or** the legacy
  bare arrays (`path[]` / `boundary[]` / `alignment[]`). Legacy arrays normalize
  with their historical closure (path → open, boundary → closed). Providing both
  spellings for one input (`path` + `boundary`, `path` + `alignment`) is a `400`.

  **`(objectType, form)` authorization matrix (DATA_MODEL §1 governance 4).**
  The dispatch checks `gen_rule::matrix::authorize(kind, form)`; combinations
  without a matrix row return **400 "creation method '<form>' is not authorized
  for object type '<kind>'"**. Authorized rows today:

  | kind | form | Genesis |
  |---|---|---|
  | `wall` | `panel` (open centerline) | Surface |
  | `wall` | `region` (closed boundary pieces) | Surface |
  | `slab` / `floor` | `region` | Surface |
  | `roof` | `region` (footprint) / `panel` (2-point profile) | Surface |
  | `road` | `linear` (open alignment) | Linear |
  | `line` | `point` (guide tube) | Point |

  Created objects record the decision as `genesis_class` / `genesis_form`
  properties. Road and line paths must be open (`closed: true` → 400); a roof
  `panel` path must have exactly 2 distinct points.

  Units are metres. `series_id` forwards the request to the catalog/series path: it selects a `ComponentDef` for metadata/series attribution, but the geometry is still produced by the hard-coded `build_wall`/`build_slab`/`build_road`/`build_pipe` mesh generators (with `param_values: HashMap::new()`). This is transitional — feature-tree/BRep via `/api/catalog/instantiate` is the official geometry path.

  Layered picked elevation (`path`/`boundary` carry `[x, y, z]`): the picked z is no longer dropped.
  - Wall `path`: the z values are preserved; when all picked z are equal the geometry is placed at that elevation (bbox min-z = picked z). If z values differ (sloped path), the simplified plan keeps the **first point's z** as the base elevation and ignores the differences (planar extrusion only, no per-point grading).
  - `boundary` (slab/roof/floor footprint): base elevation = the first boundary point's z (bottom of the lowest layer).
  - `roof` profile mode: `mode = "roof"` with a 2-point `path` (distinct start/end, no `boundary`) generates a 2-point profile roof: the span runs start→end, extruded across `width` (≤ 0 falls back to 1.0), each layer stacked along the layer normal starting at `path[0].z`; segment orientation comes from the call-site rotation by the segment angle.
  - `road` with ≥ 2 `alignment` points lays segments along the polyline honoring `width`/`thickness`.

- Response: the created `OmniObject` (with generated `geometry`).
- Errors: `404` unknown `wall_id` (door/window), `400` (empty layers, < 2 alignment points, unsolvable series, **invalid `boundary`** — `validate_boundary` rejects < 3 points, collinear points, zero-length edges, degenerate area, and self-intersecting (bowtie) closed boundaries, with the reason in the message; wall `path` requires ≥ 2 distinct points), plus propagates GenRule engine errors.

```bash
curl -sS -X POST "$BASE/api/genrule" -H 'Content-Type: application/json' \
  -d '{"type":"wall","name":"Wall A","length":5,"height":3,"core_thickness":0.2,"finish_thickness":0.02,"start_x":0,"start_y":0,"start_z":0,"end_x":5,"end_y":0,"end_z":0}'
curl -sS -X POST "$BASE/api/genrule" -H 'Content-Type: application/json' \
  -d '{"type":"layered","mode":"wall","name":"Cavity wall","height":3,"layers":[{"name":"brick","thickness":0.1},{"name":"insulation","thickness":0.08}]}'
```

## AMIR Endpoints

AMIR is the AI layer (natural language ⇄ Omcom). **AMIR must be configured** via `AMIR_PROVIDER` + `AMIR_API_KEY` (optional `AMIR_MODEL`); otherwise `/api/amir/translate`, `/chat`, and `/describe` return **`501 Not Implemented`**.

| Method & Path | Purpose |
|---|---|
| `POST /api/amir/translate` | Natural language → Omcom commands. |
| `POST /api/amir/chat` | Multi-turn conversation (with commands). |
| `POST /api/amir/describe` | Model objects → natural language description. |
| `POST /api/amir/explain` | Validation errors → plain-language explanations. |

- `POST /api/amir/translate` body: `{ "text": "Create a 5m wall", "selected_ids": [] }` → `AmirTranslateResponse`: `{ success, commands (JSON objects), summary, errors }`.
- `POST /api/amir/chat` body: `{ "session_id": null, "text": "...", "selected_ids": [] }` → `AmirChatResponse`: `{ session_id, reply, commands, summary }` — echo back `session_id` on the next turn to continue the conversation.
- `POST /api/amir/describe` body: `{ "object_ids": [], "format": "text" | "json" }` (null = whole project) → `{ "description": "..." }`.
- `POST /api/amir/explain` body: `{ "errors": ["...raw validator errors..."], "context": "optional" }` → `{ "explanations": ["..."] }`. This one works even without an LLM (returns a stub message).
- LLM/provider failures surface as `502`; parse problems as `422`; unsupported intents / missing parameters as `400`; unknown references as `404`; conflicts as `409`.

```bash
curl -sS -X POST "$BASE/api/amir/translate" -H 'Content-Type: application/json' \
  -d '{"text":"Create a 5m long 3m high wall","selected_ids":[]}'

curl -sS -X POST "$BASE/api/amir/describe" -H 'Content-Type: application/json' \
  -d '{"object_ids":null,"format":"text"}'
```

## Static Files

Any request that does not match an `/api/*` route falls back to `ServeDir::new("web")` — the compiled web front-end is served from the `web` directory relative to the server's working directory. Visiting `http://localhost:3000/` opens the UI.

## Status Codes and Error Handling

- `200` success (empty body for most mutators), `201` for successful catalog/series sub-resource creations.
- `204` for successful sketch deletes and catalog definition/param deletions.
- `400` bad request (invalid enums, no geometry, invalid relation, engine errors reported as plain text body).
- `404` unknown object referenced by an existing route; misspelled routes fall through to the static-file fallback instead of returning `404`.
- `500` internal (e.g., Omcom execution failure inside `POST /api/objects`).
- `501` AMIR endpoints without configuration; `502` LLM/provider errors; `422` parse errors.
- Mutating endpoints with `OMNIM_PROJECT` set auto-save the project to that path (failures are logged, not surfaced to clients).
