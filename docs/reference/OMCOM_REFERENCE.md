# OmniCommand Reference — the typed command system

Last updated: 2026-10-27

> **Note.** The Omcom *text* surface is a draft RFC (RFC-0001), not implemented; see [../RFC/RFC-0001-omcom-text-dsl.md](../RFC/RFC-0001-omcom-text-dsl.md).
> What actually ships today is the **typed** command system described here: a Protobuf-defined
> `OmniCommand` envelope (sent as JSON), validated and executed by the Rust crate
> `crates/omcom` (`omnim_omcom`).

---

## 1. What OmniCommand is

OmniCommand is the single, typed protocol through which every mutation of an Omnim project
flows. One `OmniCommand` message carries an action code, an actor, an optional target, and a
list of concrete `Operation` messages. There is **no grammar to parse**: the operations are
typed messages defined in [`proto/omcom.proto`](../../proto/omcom.proto), compiled by
[`prost`](https://docs.rs/prost) into Rust types with `serde` support — which means the same
command can be produced, serialized as **JSON** (snake_case field names, enums as integers),
and posted straight to the server.

Sources of commands:

- **The web Omcom console** builds `OmniCommand` objects and sends them as JSON.
- **The REST API** — `POST /api/omcom` accepts a serialized `OmniCommand`;
  see [API.md](API.md) for the full endpoint list.
- **AI agents and other clients** produce the same JSON structure through actor type
  `ACTOR_TYPE_AI_AGENT` (2).

Execution is handled by `crates/omcom/src/lib.rs` (~3,645 lines, single file), which contains
three layers:

1. **`Validator`** — checks the command against the current `Project` state *before* anything
   is mutated. Validation failures abort the whole command.
2. **`Executor`** — applies each `Operation` to the project, recording an inverse `Command`
   for each mutation so it can be undone.
3. **`undo` / `redo` / transactions** — a bounded history (depth 200) plus an explicit
   transaction API (`begin_transaction` / `commit` / `rollback`).

### Validation and transaction semantics in one paragraph

`Executor::execute` first calls `Validator::validate`, which returns a list of error strings;
any error short-circuits the command (`ExecutionResult { success: false, message: "Validation
failed: …" }`). If validation passes, operations are applied in order; each mutation pushes an
inverse `Command` onto the transaction stack. If an operation fails mid-way (e.g. a containment
cycle), the executor rolls back the commands applied so far (`fail_and_rollback`) and returns a
failure. When the executor is inside a `begin_transaction()` block, commands are staged and
only pushed into the undo stack on `commit()`; `rollback()` applies their inverses immediately.
The undo stack holds at most **200** commands (`MAX_UNDO_DEPTH`); pushing more evicts the
oldest. Any new execution also clears the redo stack.

## 2. The command envelope

`OmniCommand` (`proto/omcom.proto`)：

| Field | JSON name | Type | Notes |
|---|---|---|---|
| version | `version` | `string` | envelope version |
| id | `id` | `string` | **must be non-empty** (Validator error `instruction id is empty`) |
| action | `action` | `Action` (int enum) | one value from the action enum, see Appendix A |
| actor | `actor` | `Actor` | `{ id, type }` |
| target | `target` | `Target` (oneof) | optional; used by property/material actions |
| operations | `operations` | `Operation[]` | the work to perform; most actions use exactly one |
| validation | `validation` | `ValidationResult` | set by the server after validation |
| timestamp | `timestamp` | `Timestamp` | `{ seconds: int64, nanos: int32 }` |
| metadata | `metadata` | `map<string,string>` | free-form |

### Actor type (enum `ActorType`)

| Value | Name | Meaning |
|---|---|---|
| 0 | `ACTOR_TYPE_UNSPECIFIED` | unset |
| 1 | `USER` | human user |
| 2 | `AI_AGENT` | AI agent |
| 3 | `SYSTEM` | system |
| 4 | `IMPORT` | import pipeline |

### Target (oneof `target_type`)

```json
{ "objectId": null }  ← illustrative; see below for the real shapes
```

| Variant | JSON shape | Used for |
|---|---|---|
| `object` | `{"object": {"object_id": "…"}}` | `SET_PROPERTY`, `DELETE_PROPERTY`, `ADD_PROPERTY_SET`, `SET_MATERIAL`, `TRANSFORM_GEOMETRY`, and object-level lifecycle targets |
| `geometry` | `{"geometry": {"geometry_id": "…"}}` | geometry-level actions |
| `selection` | `{"selection": {"object_ids": ["…"]}}` | batch / console selections |
| `scene` | `{"scene": {"scene_id": "…"}}` | whole-scene actions |
| `lifecycle` | `{"lifecycle": {"record_id": "…"}}` | lifecycle record actions |

The `Target` is where the Validator and the executor look up the affected object for
`SET_PROPERTY`, `ADD_PROPERTY_SET`, and a handful of other actions; most other operations carry
their own `*_id` fields.

> **JSON encoding note.** As generated by prost + serde, enums serialize as **integers**
> (`"action": 1` for `CREATE_OBJECT`), field names are snake_case, and proto3 `optional`
> fields appear as `null` when unset. The oneof `target.target_type` serializes as a single
> key such as `{"object":{"object_id":"…"}}`.

## 3. Operation families

`Operation` is a oneof with **51 variants** (`create_geometry` … `load_series`). They group
naturally into the families below. For each operation: the message name, its key fields
(JSON snake_case; enum-typed fields are integers), what the Validator checks, and what the
Executor mutates. Unless stated otherwise, IDs are UUID strings issued by the system.

### 3.1 Object creation & modification

**`create_object` → `CreateObjectOperation`** (action `CREATE_OBJECT` = 1)

- Fields: `type` (ObjectType, int), `name`, `description`, `geometry` (ParametricGeometry),
  `properties` (Property[]), `parent_id`.
- Validator: object type must be a valid `ObjectType`; `name` non-empty; `parent_id` (if set)
  must exist. Spatial overlap with existing object bounding boxes is logged as a **warning**
  (stderr), not an error — overlaps are common in real engineering.
- Executor: creates the `OmniObject`, builds real geometry from the `ParametricGeometry`
  (via `omnim_model::geometry::create_geometry`), inserts it, and returns the new ID in
  `created_ids`.

**`modify_object` → `ModifyObjectOperation`**

- Fields: `object_id`, optional `new_name`, `new_description`, `new_geometry`.
- Validator/Executor: target object must exist; snapshot taken (name/description/geometry)
  for undo.

**`copy_object` → `CopyObjectOperation`**

- Fields: `source_object_id`, `new_name`, `parent_id`.
- Validator: source must exist, target parent (if set) must exist.
- Executor: deep-copies the object with a new UUID; undo deletes the copy.

**`move_object` → `MoveObjectOperation`**

- Fields: `object_id`, `new_parent_id`.
- Validator: both must exist.
- Executor: re-parents; undo restores the old parent.

### 3.2 Properties & relations

**`set_property` → `Property`**, action `SET_PROPERTY` (20). The `Target.object` carries the
object; `Property` is `{ name, value, unit, description }` where `value` is a oneof
(`string_value`, `int_value`, `double_value`, `bool_value`, `point_value`, `vector_value`,
`binary_value`, `timestamp_value`). Validator: target object must exist. Undo restores the old
value (or removes the property if it did not exist).

**`delete_property` → `DeletePropertyOperation`** (`name`). Undo restores the removed property.

**`add_property_set` → `PropertySet`** (`{ name, description, properties }`). Appended to
`Target.object`'s property sets.

**`remove_property_set` → `RemovePropertySetOperation`** (`name`). Undo restores the set.

**`add_containment` → `Containment`** (`{ parent_id, child_id, … }`). Validator: both objects
must exist. Executor: `project.relations.add_containment` — this is the one place where the
library itself can reject an operation (e.g. cycles), triggering the executor's mid-command
rollback path. Undo removes the containment.

**`remove_containment` → `RemoveContainmentOperation`** (`parent_id`, `child_id`). Undo restores it.

**`add_connection` → `Connection`** (`from_object_id`, `to_object_id`, …). Validator: both
endpoints must exist. Undo removes the connection.

**`remove_connection` → `RemoveConnectionOperation`** (`from_object_id`, `to_object_id`).

### 3.3 Materials

**`set_material` → `SetMaterialOperation`** (`object_id`, `material_id`). Validator: both the
object and the material must exist in the project's material library. Executor sets
`obj.material_id`; undo restores the previous `material_id` (including "none").

### 3.4 Geometry: create / transform / array / boolean

**`create_geometry` → `ParametricOperation`** (action `CREATE_GEOMETRY` = 10). An alternative
geometry authority from `create_object`'s inline geometry — a `ParametricGeometry` of
`ParametricOperation`s: `box`, `cylinder`, `sphere`, `cone`, `extrusion`, `revolve`, `sweep`,
`loft`, `torus`, `dish` (from `omnim.proto`). Validator: action-level target object must exist.

**`transform_geometry` → `TransformGeometryOperation`**

- Fields: `object_id`, optional `translation` (Point3D), `rotation` (Rotation, quaternion
  x/y/z/w), `scale` (Vector3D).
- Validator: object must exist. Executor: bakes the transform into the object's geometry;
  undo restores the old geometry.

**`array` → `ArrayOperation`**

- Fields: `source_object_id`, `pattern` (string: `"linear"` / `"rectangular"` / `"circular"`),
  `count_x/y/z` (int32, clamped to ≥1), `spacing_x/y/z` (double).
- Validator: source must exist. Executor: duplicates the source for every `(ix,iy,iz) ≠ (0,0,0)`
  cell with a fresh UUID and name suffix `"Name (i,j,k)"`, offsetting geometry by
  `i*spacing_i`; undo deletes all the copies.

**`boolean` → `BooleanOperation`**

- Fields: `type` (string: `"union"` / `"subtract"` / `"intersect"`), `target_object_id`,
  `operand_object_ids` (repeated).
- Validator: target and every operand must exist. Executor applies the mesh booleans
  (`omnim_mesh`); undo restores the pre-boolean target geometry.

### 3.5 Sketches

Sketch entities use 1-based indices, constraints reference entities via `SketchPointRef`
(`entity_index` 1-based, `point_index` 0=free/1=start/2=end). Entity types (`SketchEntityType`):
point, line, circle, arc, workplane, rectangle, polygon, ellipse, spline, polyline.
Constraint types (`SketchConstraintType`): horizontal, vertical, coincident, parallel,
perpendicular, length, distance, angle, radius, diameter, tangent, symmetric, fixed,
at_midpoint, equal_length, equal_radius, pt_on_line, pt_on_circle, same_orientation.

| Operation (oneof) | Message | Key fields | Validator | Executor |
|---|---|---|---|---|
| `create_sketch` | CreateSketchOperation | `name`, `origin` (Point3D), `normal` (Vector3D; `(0,0,0)` = free 3D) | — | creates sketch; undo deletes it |
| `add_sketch_entity` | AddSketchEntityOperation | `sketch_id`, `entity` (SketchEntityData) | sketch exists | appends entity; undo removes by index |
| `add_sketch_constraint` | AddSketchConstraintOperation | `sketch_id`, `constraint` (SketchConstraintData) | sketch exists | appends constraint; undo removes |
| `solve_sketch` | SolveSketchOperation | `sketch_id` | sketch exists | runs `omnim_sketch` solver; undo restores `solved` flag |
| `delete_sketch_entity` | DeleteSketchEntityOperation | `sketch_id`, `entity_index` (1-based) | sketch exists | undo re-inserts entity |
| `remove_sketch_constraint` | RemoveSketchConstraintOperation | `sketch_id`, `constraint_index` (1-based) | sketch exists | undo re-inserts constraint |
| `delete_sketch` | DeleteSketchOperation | `sketch_id` | sketch exists | undo restores the sketch |
| `extrude_sketch` | ExtrudeSketchOperation | `sketch_id`, `depth`, `direction` | sketch exists | creates a 3D body from the closed profile; undo deletes it |
| `revolve_sketch` | RevolveSketchOperation | `sketch_id`, `angle` (radians, 0=full 360°), `axis_origin`, `axis_direction` | sketch exists | creates a revolved body; undo deletes it |

Direct sketch extrusion/revolution is also reachable via `add_feature` (`ADD_FEATURE` = 111).

### 3.6 Components & the feature tree

Components own ordered feature lists; features reference sketches and may cache mesh
geometry. `FeatureType`: extrude(1), revolve(2), sweep(3), loft(4), boolean(5), chamfer(6),
fillet(7), pattern(8), shell(9), fusion(10), lofted_fusion(11).

| Operation | Message | Key fields | Validator | Executor |
|---|---|---|---|---|
| `create_component` | CreateComponentOperation | `name`, `parent_id` | — | creates component; undo deletes |
| `add_feature` | AddFeatureOperation | `component_id`, `feature_type`, `sketch_id`, `depth`/`direction` (extrude), `angle`/`axis_origin`/`axis_direction` (revolve), `is_cut`, `input_sketch_ids` (sweep path / loft sections), `axis_sketch_id` | component object exists; sketch exists | adds feature; undo removes it |
| `remove_feature` | RemoveFeatureOperation | `component_id`, `feature_id` | component exists | undo restores the feature |
| `rebuild_features` | RebuildFeaturesOperation | `component_id`, optional `feature_id` (rebuild from it onward; omit = rebuild all) | — | regenerates component geometry; rebuild is idempotent, no undo op |

### 3.7 Catalog publish (library components)

These operate on the global component library (`omnim_model::catalog`, in `LIBRARY`), not on
project objects.

| Operation | Message | Key fields | Validator | Executor |
|---|---|---|---|---|
| `define_component` | DefineComponentOperation | `name`, `category`, `description`, `ifc_class`, `standard_reference`, `tags`, `domain` | name non-empty | registers ComponentDef; undo removes it |
| `add_component_param` | AddComponentParamOperation | `component_id`, `param_name`, `param_type` (ParamType int), `default_value`, `min_value`, `max_value`, `step`, `unit`, `formula`, `choices`, `description` | catalog component exists | appends param; undo removes by index |
| `add_connector` | AddConnectorOperation | `component_id`, `connector_id`, `connector_name`, position/direction/`bore` *expression* fields (`position_x_expr` etc.), `connection_type_code`, `role` (ConnectorRole int) | component exists | appends ConnectorDef; undo removes |
| `publish_component` | PublishComponentOperation | `component_id` | component exists | marks published |
| `delete_component_def` | DeleteComponentDefOperation | `component_id` | component exists | undo restores the def |

`ParamType`: unspecified 0, length 1, angle 2, integer 3, choice 4, boolean 5, ratio 6.
`ConnectorRole`: unspecified 0, inlet 1, outlet 2, bidirectional 3, mount 4, branch 5.

### 3.8 Series library (spec-driven selection)

Spec-book series: a `Selector` tree of questions and answers, each answer binding spec
components and parameter constraints.

| Operation | Message | Key fields | Validator | Executor |
|---|---|---|---|---|
| `create_series` | CreateSeriesOperation | `name`, `description`, `domain`, `standard_reference` | — | creates Series |
| `add_selector` | AddSelectorOperation | `series_id`, `selector_id`, `question` | series exists | appends selector |
| `add_answer` | AddAnswerOperation | `series_id`, `selector_id`, `answer_id`, `answer_value`, `is_numeric_range`, `range_min`, `range_max` | series exists | appends answer; undo removes by index |
| `add_spec_component` | AddSpecComponentOperation | `series_id`, `selector_id`, `answer_id`, `component_def_id`, `material`, `connection_type_code` | series exists | attaches spec component |
| `add_param_constraint` | AddParamConstraintOperation | `series_id`, `component_def_id`, `param_name`, `default_value`, `min_value`, `max_value`, `step`, `fixed_value` | series exists | appends constraint |
| `delete_series` | DeleteSeriesOperation | `series_id` | series exists | undo restores the series |
| `load_series` | LoadSeriesOperation | `path`, `source` (`"standalone"` \| `"library"`) | path non-empty | loads the series from disk; undo removes the loaded IDs |

### 3.9 Lifecycle, schedule, cost, progress, work orders

All operate on `ProjectLifecycleRecord`s in the project.

| Operation | Message | Key fields | Validator | Executor |
|---|---|---|---|---|
| `create_lifecycle_record` | CreateLifecycleRecordOperation | `phase` (LifecyclePhase int), `name`, `description`, `record_type`, `related_object_ids`, `properties` | — | creates record with status `Draft`(1); undo deletes |
| `modify_lifecycle_record` | ModifyLifecycleRecordOperation | `record_id`, optional `name`/`description`, optional `status` (RecordStatus int), `properties` | record exists | undo restores old name/description/status |
| `delete_lifecycle_record` | DeleteLifecycleRecordOperation | `record_id` | record exists | undo restores the record |
| `link_record_to_object` | LinkRecordToObjectOperation | `record_id`, `object_id`, `link_role` | both exist | undo unlinks |
| `update_schedule` | UpdateScheduleOperation | `record_id`, optional `planned_start`/`planned_finish`/`actual_start`/`actual_finish` (Timestamp) | record exists | undo restores the old timestamps |
| `update_cost` | UpdateCostOperation | `record_id`, `planned_cost`, `actual_cost`, `currency` | record exists | undo restores the old costs |
| `update_progress` | UpdateProgressOperation | `record_id`, `percent_complete` (0–100), `note` | record exists | undo restores the old percent |
| `create_work_order` | CreateWorkOrderOperation | `asset_object_id`, `title`, `description` | asset object exists | creates a work-order record (maintenance phase); undo deletes |
| `update_work_order` | UpdateWorkOrderOperation | `work_order_id`, `status`, `description` (strings) | — | undo restores old status/description |

`LifecyclePhase`: unspecified 0, planning 1, design 2, procurement 3, construction 4,
commissioning_acceptance 5, asset 6, operation_maintenance 7, production 8, decommissioning 9.
`RecordStatus`: unspecified 0, draft 1, open 2, in_progress 3, blocked 4, completed 5,
approved 6, rejected 7, closed 8.

### 3.10 Action families without dedicated operations

Some action codes have no `Operation` variant yet; they are reserved at the executor layer or
handled by other services:

- `IMPORT_FILE` (60), `EXPORT_FILE` (61), `PARSE_TO_OMCOM` (62) — import/export pipeline
  (see the API reference).
- `MODIFY_GEOMETRY` (11), `DELETE_GEOMETRY` (12) — reserved messages noted in the proto
  (`ModifyGeometryOperation`/`DeleteGeometryOperation`).
- `BATCH_DELETE` (41), `BATCH_TRANSFORM` (42) — reserved.
- `ADD_COMPONENT_FEATURE` (203) — reserved message noted in the proto.
- `INGEST_SENSOR_DATA` (82), `VALIDATE` (90), `LIST_CATALOG` (205), `LIST_SERIES` (215) —
  read/misc actions handled by their respective layers.
- `ADD_CONNECTOR`'s sibling `ADD_ANSWER` etc. are fully wired (see §3.8); the gaps above are
  the only ones.

## 5. Command lookup conventions

OmniCommand is JSON. Rectangular JSON is the wire format; there is no textual DSL. Two
conventions to remember when hand-writing commands:

- **Enums are integers**; enums serialize as their integer code.
- **IDs are UUIDs** minted by the executor itself. You must first create the object to get its ID — there is no way to predict the auto-generated ID before execute. Referencing a *pre-existing* object requires first querying the project to obtain that object's real ID.

### POST /api/omcom — create a wall

```json
{
  "version": "1.0",
  "id": "cmd-20261027-0001",
  "action": 1,
  "actor": { "id": "user-alice", "type": 1 },
  "target": null,
  "operations": [
    {
      "createObject": {
        "type": 100,
        "name": "Wall A",
        "description": "Exterior wall on level 1",
        "geometry": {
          "operations": [
            { "box": { "length": 6000.0, "width": 200.0, "height": 3000.0 } }
          ]
        },
        "properties": [
          { "name": "FireRating", "value": { "stringValue": "2h" } }
        ]
      }
    }
  ],
  "metadata": { "source": "console" }
}
```

### POST /api/omcom — set a material

```json
{
  "version": "1.0",
  "id": "cmd-20261027-0002",
  "action": 50,
  "actor": { "id": "user-alice", "type": 1 },
  "operations": [
    { "setMaterial": { "object_id": "<uuid-of-wall-a>", "material_id": "<material-uuid>" } }
  ]
}
```

(`material_id` must reference a material already defined in the project's material library —
the Validator rejects unknown materials. When the field is a per-message scalar, prost's
serde name is the snake_case from the proto (`material_id`); this is exactly how the
console on the web sends it.)

### POST /api/omcom — extrude a sketch

```json
{
  "version": "1.0",
  "id": "cmd-20261027-0003",
  "action": 107,
  "actor": { "id": "agent-7", "type": 2 },
  "operations": [
    { "extrudeSketch": {
        "sketch_id": "<sketch-uuid>",
        "depth": 400.0,
        "direction": { "x": 0.0, "y": 0.0, "z": 1.0 }
    } }
  ]
}
```

A successful response is an `ExecutionResult`:

```json
{ "success": true, "message": "…", "created_ids": ["<new-object-uuid>"] }
```

A failed response has `success: false` and a `message` starting with `"Validation failed: …"`.
