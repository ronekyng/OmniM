## 1. 执行摘要

本轮审计的核心结论不是“功能还不够”，而是：

> **文档集里存在“诚实层”和“愿景层”，但两层没有隔离。**  
> `docs/status/ROADMAP`、`FORMAT_COMPAT`、`CHANGELOG` 是诚实的；`README`、`IFC_EXTENSION` 和部分 `specification/` 仍按愿景写。读者从 README 进入，会得到一套与代码不符的能力预期。

更严重的是，文档承诺的三条基础契约在当前代码里都不成立：

1. **单一写入路径**：并非所有变更都经过 `Validator` + `Executor`；
2. **完整撤销/重做**：大量直接写 `Project` 的端点不在撤销栈内；
3. **变更后自动保存**：只有少数端点落盘，默认配置甚至完全不落盘。

此外，目录/系列并没有成为几何生成的唯一真值：工具栏、构件面板、Omcom 控制台、IFC 导入各自走不同路径，产生不同的对象类型、几何来源和持久化行为。

## 3. P0 发现：基础契约与上手路径

### P0-1 快速开始按文档执行会连续失败

`docs/guides/GETTING_STARTED.zh-CN.md`：

| 文档指令 | 实际情况 | 证据 |
|---|---|---|
| 在 Omcom 控制台输入 `CREATE Object name:"Wall-01"`（第 53–57 行） | 控制台只识别 `CREATE_OBJECT <type> <name>` 或 JSON；`CREATE Object…` 不是有效命令 | `web/src/app/components/OmniPanel.tsx:340-365` |
| `curl -d '{"command": "UNDO"}'` 到 `/api/omcom`（第 62–64 行） | `/api/omcom` 接收完整 `OmniCommand` 信封，不是 `{"command":"UNDO"}`，不会触发撤销 | `crates/server/src/lib.rs:863-871` |
| `curl -F "file=@…"` 导入 IFC（第 71 行） | `/api/import/ifc` 接收**原始 IFC 文本**，不是 multipart；正确写法是 `--data-binary @file` | `crates/server/src/lib.rs:2220-2227`、`docs/reference/API.zh-CN.md:300` |
| “服务器把数据持久化到普通 JSON 文件”（第 16 行） | 默认 `project.omnim` 的 `save_path` 实际是 `None`，默认启动根本不落盘 | `crates/server/src/main.rs:47-51` |

这是最不该出错的文档：用户第一次上手就会失败。

### P0-2 “所有变更走同一 Executor/Validator，完整撤销”不成立

`ADR-0006`（`docs/architecture/DECISIONS.zh-CN.md:163-176`）明确写：

> 变更管线只有一条：构造 `OmniCommand` → `Validator` → `Executor` → 记录撤销历史。**每个**来源都走同一个 Validator/Executor。任何路径都不得绕道写 `Project`。

`PLATFORM_ARCH` §1、`DATA_FLOW` §0 也这样写。

静态扫描 `crates/server/src/lib.rs` 的结果：

- 55 个持有 `project.write()` 的 handler 中，只有 13 个出现 `executor`；
- 约 42 个直接改 `Project`，包括：改名、设属性、材质、父子关系、连接、测量、生命周期、草图更新/求解、IFC 导入、目录实例化、全部系列编辑。

直接写路径示例：

- `update_object`（`server:287`）
- `transform_object`（`server:413`）
- `set_parent`（`server:475`）
- `connect`（`server:484`）
- `create_material` / `assign_material`（`server:506/527`）
- `update_sketch` / `solve_sketch` / `update_sketch_entity`
- `import_ifc`（`server:2220`）
- `instantiate_from_catalog`（`server:3560`）
- 全部 `create_series_handler` / `add_selector_handler` / `add_answer_handler` 等系列编辑

**影响**：改名、赋材质、连管道、改系列、导入 IFC、放置目录构件，撤销按钮都无效。文档却宣称“完整撤销/重做”。

> 说明：静态扫描可能把只读 handler（如 `section_handler`）误计为写 handler；但 55/13 的量级足以证明“所有路径”不成立。

### P0-3 “变更后自动保存”不成立，默认配置甚至不保存

同一扫描中，只有 5 个 handler 调用 `p.save`：

- `update_object`
- `add_feature`
- `update_feature`
- `remove_feature`
- `rebuild_component`

以下主路径全部**不保存**：

- `POST /api/objects`（创建对象）
- `POST /api/genrule`（工具栏建墙/板/路/管）
- `POST /api/omcom`（所谓统一命令入口）
- `POST /api/catalog/instantiate`（构件面板放置）
- `POST /api/import/ifc`（IFC 导入；`mode=replace` 会直接覆盖项目）
- 所有 `/api/series/*` 系列编辑

再叠加默认 `save_path=None`：

- 默认启动时，建模、导入、放置构件都可能只存在于内存；
- 即使设置了非默认 `OMNIM_PROJECT`，多数端点仍然不主动保存。

**影响**：用户可能丢失整个建模会话。这不是性能问题，是数据安全问题。

### P0-4 目录/系列没有驱动几何，存在三套并行建模路径

| 用户动作 | 端点 | 几何来源 | 对象类型 | 撤销 | 保存 |
|---|---|---|---|---|---|
| 工具栏建墙/板/路/管 | `/api/genrule` | 硬编码 mesh；`series_id` 只用于选 `ComponentDef`，`param_values` 为空 | Wall/Slab/Road/Pipe | ✅ | ❌ |
| 构件面板放置 | `/api/catalog/instantiate` | 特征树 → BRep/mesh | **`Component`** | ❌ | ❌ |
| 通用创建 | `/api/objects` | 无几何 | 指定类型 | ✅ | ❌ |
| Omcom 控制台 | `/api/omcom` | 类型化操作 | 按操作 | ✅ | ❌ |
| IFC 导入 | `/api/import/ifc` | 导入 mesh；merge/replace | 映射类型 | ❌ | ❌ |
| 改名/材质/连接/移动 | `/api/objects/...` | 直接改 Project | — | ❌ | 仅改名保存 |
| 目录/系列编辑 | `/api/series/...` | 直接改 SeriesStore | — | ❌ | ❌ |
| 特征编辑 | `/api/components/...` | 特征引擎 | Component | ❌ | ✅（部分） |

关键证据：

- `genrule_create_catalog()` 的注释就是“Create a plain object (not a Component) with correct geometry”，随后仍调用硬编码 `build_wall/build_slab/build_road/build_pipe`，并写入 `param_values: HashMap::new()`（`crates/server/src/lib.rs:1451-1504`）。
- `instantiate_catalog_component_impl()` 虽然走特征树，但创建的是 `ObjectType::Component`，不是 `Wall/Beam/Pipe`（`crates/model/src/project.rs:253`）。
- 文档 `DATA_MODEL` §6、`CATALOG_SERIES` §2.4、`PLATFORM_ARCH` §1 都说“主要几何由目录特征树驱动”。

**结果**：同一堵墙，从工具栏建、从构件面板放、从 Omcom 建，会得到不同的对象类型、不同的几何来源、不同的撤销/保存行为。这不是实现细节，是模型语义分裂。

### P0-5 系列门禁、材质、连接兼容性都比文档弱得多

- `check_series_gate()` 只检查“构件是否从某个系列可达”（`crates/model/src/project.rs:88-103`），不校验材质、参数范围、连接等级。
- `instantiate_from_series()` 只把 `ParamConstraint.default_value` 当默认值填入，不校验 `min/max/fixed`，也**完全不应用** `SpecComponent.material`（`crates/model/src/project.rs:368-386`）。
- `Project::connect()` 只检查两个对象存在，不检查连接点、类型码、口径、压力等级，甚至不写入 `from_point/to_point`（`crates/model/src/project.rs:105-121`）。
- `ConnectorDef` 只有 `direction`，没有 `up/基准`，无法确定法兰螺栓孔或阀杆朝向（`proto/omnim.proto:506-518`）。

文档 `CATALOG_SERIES` §2.3 说“对象之间的连接通常只在连接类型码匹配时建立”，§3.4 说“只允许系列确认的构件”；实际可以 `connect(wall, pump)`，系列材质也不会落到实例上。

### P0-6 IFC 承诺与实际差了一整代

`IFC_EXTENSION.zh-CN.md`：

- §2.3 承诺“所有 IFC 实体、所有属性集与数量、0.1 mm 几何精度”的无损往返；
- §8.1 写 IFC 2x3 / IFC 4 / IFC 4x3 均“✅ 导入/导出”；
- §5.1 写“原生支持所有标准 IFC 属性集”和 `Qto_*`；
- §9 写支持 LandXML 地形交换。

而 `FORMAT_COMPAT.zh-CN.md` 写的是：

- 仅 IFC 2x3/4 子集，无 IFC 4x3 特有实体；
- 不支持材料、材料层、工程量、分类、高级 BRep/CSG/映射项；
- 很多类导出为 `IfcBuildingElementProxy`；
- STEP/DXF/GIS/glTF 全部未实现。

`DATA_MODEL` §10.1 还说 Stair/Roof 目前导出为 Proxy，`IFC_EXTENSION` 却说直接映射 `IfcStair/IfcRoof`。**两份规范对同一件事给出相反答案。**

## 4. P1 发现：跨文档硬矛盾

1. **中英文 README 是两个项目状态**
   - 英文 README 第 44 行：当前 Phase 8；
   - 中文 README 第 44 行：当前“第一阶段”；
   - 中文路线图还是旧的十阶段（WebGPU、桌面、移动、生态），英文已改成 12 阶段状态表；
   - 两版都写“1–7 完成”，但 `ROADMAP` 明确 Phase 1 只是部分完成。

2. **README 与 status 文档全面冲突**
   - README 写 IFC 2x3/4x3 原生兼容、Omcom 文本 DSL、WebSocket 实时协作、几何流式、Tauri/移动端、全平台 60 FPS；
   - `ROADMAP` 写无 WebSocket、移动/Tauri 是非目标、Phase 9/11 只是部分完成；
   - `CHANGELOG` 第 51 行明确“无 WebSocket、无 WASM 共享内核、无桌面/移动打包”。

3. **中文 `DATA_MODEL` 不是英文版的翻译，而是旧版本**
   - 中文 2324 行，英文 2880 行；
   - 中文缺 `5.6 Component Container`、`5.7.1 Feature Panel UI`、`16a Feature Template System & Profile Library`、`16.4 Equipment Domain`、`17 Object → Catalog Reference`；
   - 中文 §13/14 对应英文 §14/15，章节号整体错位；
   - 英文 §5.6 定义了 `Component.transform`（local placement），中文没有，代码也没有——**placement 不是没想到，而是在翻译/实现中丢了**。

4. **代码围栏和编号损坏**
   - 英文 `DATA_MODEL.md` 第 442–605 行缺少闭合围栏，§5.6 被吞进代码块；
   - 中文 `DATA_MODEL.zh-CN.md` 第 438–594 行把“计划中”的说明包进了 protobuf 代码块；
   - 中文 `DATA_MODEL` 有两个 `## 11`（分类映射/索引），缺 `5.4`；
   - `STORAGE_MODEL` 中英文都有两个 `## 5`。

5. **DOMAINS 列了 155 个对象，proto 只有 51 个**
   `COMPONENT_INVENTORY.md` 自己的统计（2026-08-07）：Building 37 个中 15 个只在 DOMAINS、Civil 41 个中 31 个只在 DOMAINS、Plant 39 个中 28 个只在 DOMAINS、Mechanical 38 个中 30 个只在 DOMAINS。  
   `DOMAINS` 没有状态列，读者会以为 Rebar、Connection、Alignment、Nozzle、Support、Configuration 等都已支持。

6. **GLOSSARY 有 9 个 proto 里不存在的 ObjectType**
   `OBJECT_TYPE_CUT_VOLUME`、`FILL_VOLUME`、`GRADING_SURFACE`、`SLOPE`、`SITE_COMPONENT`、`EARTHWORK_BALANCE`、`CONTROL_VALVE`、`CABLE`、`CONDUIT`。  
   术语表把它们写成现有枚举，但 `proto/omnim.proto` 没有。

7. **“Pipe 是面构件还是线构件”两份文档打架**
   `DOMAINS` §2 写“Duct, Pipe, CableTray（直段→LayerExtrusion，弯头→LinearComponent）”；`DATA_MODEL` §1/§6.4 明确 Pipe 是线构件。建模师需要唯一答案。

8. **`Project` 到底持不持有 Library**
   `CATALOG_SERIES`/`GLOSSARY` 说 Project 不持有 Library；`DATA_FLOW` §4 图里写 `Project.catalog`。

9. **生命周期引用文档 ID，但没有 Document 实体**
   `ProjectLifecycleRecord.related_document_ids` 存在，但整个数据模型没有 `Document`/`DocumentRevision`/文件/审批对象。全生命周期平台不能只有 ID 没有文档模型。

10. **`Section` 概念没有字段**
    `DATA_MODEL` §13.1 把 `Section` 列为目录组织概念（SECT），但 `ComponentDef` 没有 `section` 字段；`CATALOG_SERIES` 的字段表也没有。

11. **`ComponentDef.id` 双身份**
    文档说 `id` 是 UUID，同时“以稳定的人类可读名称引用”；`SpecComponent.component_def_id` 可存 UUID 或名称，`check_series_gate` 两种都查。改名/重名时没有明确规则，模型不可复现。

12. **`GLOSSARY` 对 `Component` / `Series` 的定义含混**
    - “Component = 由一个或多个特征组成的三维几何体，是 Object 的几何表示”；
    - 但代码里 `ObjectType::Component` 是实例类型，`ComponentDef` 是目录定义，英文 `DATA_MODEL` §5.6 又定义了一个 `Component` 容器。
    - “Series = 同类对象的集合”——实际是规格决策树，不是同类对象集合。

13. **“所有文档均提供中英双语”不成立**
    `README.zh-CN.md:228` 这样写，但 14 篇 `docs/research/*` 只有英文。研究文档恰恰是很多设计结论的依据。

14. **文档门户没有“建模师”入口**
    `docs/README.zh-CN.md` 有“上手/理解/设计契约/API/进度/参与设计”，但没有“我想建模，从哪里开始”。

## 5. P2 发现：文档工程与可维护性

- **大量文档没有更新日期/状态徽标**：审计脚本列出的无状态/日期文档约 40 篇，包括 `AMIR_SPEC`、`DOMAINS`、`LIFECYCLE`、`IFC_EXTENSION`、`API`、`GLOSSARY`。但 `docs/README` 的状态图例说“以各文档标注的更新日期为准”，无法执行。
- **代码围栏/标题编号缺少 CI 检查**：本轮发现的围栏、重复 §11、重复 `STORAGE_MODEL` §5、缺失 5.4 都是可以脚本化拦截的。
- **`CODE_DEVIATIONS` 漏掉了本轮最严重的偏差**：单一写入路径、自动保存、目录几何路径、系列材质/参数强制、连接兼容性、ObjectType::Component。
- **API 路由数“约 100 条”与实际 78 条不符**（`PLATFORM_ARCH`、`CHANGELOG`、`README` 都有类似说法）。
- **`COMPONENT_INVENTORY` 更新于 2026-08-07**，而当前文档是 2026-10-27；对象数量、proto 覆盖已变化。
- **研究文档只有英文**：14 篇 `docs/research/*` 无中文版；`README.zh-CN` 的“全双语”承诺不成立。
- **规范/调研/现状混在一起**：`DATA_MODEL` 2324 行中同时包含“已实现”“设计规范”“调研笔记”“待决问题”，读者很难判断哪一段是契约。
- **缺少面向建模师的 capability matrix / handbook**：目前文档以 schema 和 crate 为中心，不以“我今天能不能建这个”组织。

### 做得好的地方

- 内部链接 **0 坏链**（脚本校验）。
- 服务器 **78 条路由全部在 `API.md` 中有文档**（去重后）。
- `OMCOM_REFERENCE` 与 `Action` 枚举基本对齐。
- `ROADMAP` / `FORMAT_COMPAT` / `CHANGELOG` 的“诚实性说明”值得保留，应成为其他文档的模板。

## 8. 待决问题

1. **代码是真相，还是设计是真相？**  
   如果代码是真相，`README`/`IFC_EXTENSION` 必须重写；如果设计是真相，代码缺口要进 `CODE_DEVIATIONS`，`README` 要标“愿景”。

2. **单一写入路径是必须恢复的架构不变量，还是允许“命令路径 + 直接 REST 路径”并存？**  
   如果并存，撤销、校验、保存、权限规则必须分别定义，不能再写“所有变更走同一门”。

3. **中文版是持续维护的翻译，还是一次性快照？**  
   目前中文 `DATA_MODEL` 已明显落后于英文，继续假装同步会持续误导中文建模师。

4. **自动保存是每请求保存，还是显式保存？**  
   当前默认配置不保存；这必须成为文档首页的显著警告，而不是藏在 `BUILDING.md` 的一句“非默认路径在变更后回写”。

5. **目录/系列几何以哪条路径为准？**  
   `/api/genrule` 的硬编码 mesh，还是 `/api/catalog/instantiate` 的特征树/BRep？这决定“参数化构件”是否是产品真值。
